# Goal + Harness：Web 全栈交付首轮设计

日期：2026-09-08

状态：正式设计已获用户确认。2026-09-08 按用户交接授权补充结构与复杂度改进的实施、验收边界；这不代替详细实施计划审阅、运行时实现或安装授权。实现、发布和安装同步尚未开始。

## 1. 已确认的产品决策

- 定位为面向 Web 全栈应用的 AI 工程工作流，不再以覆盖所有软件项目为首轮目标。
- 覆盖需求、数据、后端、前端、联调、测试与约定的运行或部署交付。
- 没有必须优先支持的技术栈；核心规则不绑定框架，存量项目优先沿用既有技术栈。
- 以 `.codex` 版本为内容基线；保留 `.agents` 的禁用状态，不删除文件，也不恢复其旧式 Skill 调度链。
- 按完整业务结果组织交付，而不是仅按前端、后端或文档完成数量报告进度。
- 首轮固化交付契约、业务切片、验收台账、证据失效和交付评测；暂缓完整恢复命令、Provider 扩展和全技术栈覆盖承诺。

成功主张必须限定为实际验证过的行为和环境。技术栈无关的契约不等于已经验证任意技术栈。

## 2. 范围与非目标

### 2.1 本轮交付范围

1. Goal 能形成可理解、可修订、具有验收边界的交付契约。
2. Harness 能按业务切片组织跨数据、API、UI、权限和运行环境的工作。
3. 每项必需验收要求关联实际证据，缺失、失败和过期证据不能被总结文本覆盖。
4. Closure 区分本轮范围验收、整个项目退出条件以及实际部署事实。
5. 新规则具有契约级、事件回放级和真实全栈夹具级验证，不用关键词命中率代替交付能力。

### 2.2 明确不做

- 原生移动应用、桌面应用、嵌入式和独立 SDK 开发画像。
- 固定技术栈脚手架、自动迁移技术栈、通用 DAG 调度器或新的 Agent 运行时。
- Fast Run、Provider 市场、Agent 产品画像、完整 pause/resume/history/timeline 命令。
- 默认启用 GSD、重新启用 `.agents` 或增加并行工作流所有者。
- 云端遥测、加密执行证明、生产自动发布、自动 Git 提交或推送。
- 重编号 Layer 0–6，或直接启用此前计划中的 state schema v2。

仅就本工作包而言，本轮设计替代 2026-09-06 Capability Provider 设计的首轮产品范围与优先级，不宣称那份设计中的能力已经实现。保留其中的职责分离和保证边界；延期功能不自动删除。“本轮不实现”不撤销其他任务的既有授权，不要求停止其 Foundation/Adapter 工作，接口协调见第 12 节。

## 3. 方案选择

| 方案 | 取舍 | 决定 |
| --- | --- | --- |
| 固定技术栈脚手架 | 容易演示，但会把方法与框架生命周期绑定，并限制存量仓库 | 不采用 |
| 先建通用适配与 Provider 平台 | 扩展面大，但会推迟最小交付闭环，并引入新的治理复杂度 | 暂缓 |
| 技术栈无关契约 + 既有 Harness + 有界验收模型 | 复用现有框架，以可验证的业务结果为中心，按已测环境声明能力 | 采用 |

## 4. 所有权与兼容边界

| 组件 | 本轮职责 | 不得承担的职责 |
| --- | --- | --- |
| Goal | 捕获用户意图、范围、约束、分类与确认；展示契约变更 | 不另建层门状态机，不覆盖 Harness 验收结论 |
| Harness | 业务切片、验收台账、证据充分性判断、层门、最小回滚和 Closure | 不把声明等同于执行，不成为被开发应用的运行时 |
| Guard | 有界结构校验、转换约束、变更序列、证据绑定及一致性审计 | 不判断业务需求是否正确，不保证外部命令诚实执行 |
| 验证工具 | 在明确环境中执行检查并提供可定位的结果 | 不自行降低验收标准，不宣布项目整体完成 |

保留 `bootstrap/maintenance`、Layer 0–6 以及现有 `scope_result`、`operation_state` 的职责和词汇。本轮接受的业务切片不自动代表整个 bootstrap 已满足退出条件。

### 4.1 状态扩展选择

采用现有工作区 `goal-state.json` 中可选的 `delivery` 扩展，不再增加第二份可写状态事实源。独立的 Markdown 摘要或导出报告只是投影，不能反向覆盖运行状态。

`delivery` 的逻辑分区固定为 `schema_version`、`profile`、`contract`、`slices`、`criteria`、`evidence` 和 `invalidations`。扩展内部的 `schema_version` 初始为 1，`profile` 为 `web-fullstack`；不与外层 Goal state schema 版本混用。

这是待实现的增量接口，不是当前 Guard 已支持的字段。实现必须满足：

- 旧的、不含 `delivery` 的合法状态继续按既有规则运行，不自动迁移或激活新行为。
- 新的 Web 全栈运行只有在 Guard 明确声明支持 `web-fullstack-delivery-v1` 时才启用扩展。版本 major 相同不足以证明该功能可用。
- 扩展在新运行初始化时绑定；同一活动运行不能通过删除扩展、修改 profile 或回退 schema 绕过新验收规则。
- 已有活动运行本轮不做原地启用；完成原有运行后，在用户确认的新受治理运行中采用新契约。
- 保存仍通过 Guard 的现有锁、相邻转换与原子写入路径完成；验收明细不形成第二个 workflow owner。
- 初版使用有界摘要和证据引用，不把完整日志或无界历史放入状态。单个运行最多保存 128 个业务切片、512 个验收项、2048 条证据索引和 256 条失效记录；`delivery` 的确定性紧凑 UTF-8 JSON 编码不得超过 2 MiB，任一限制达到时均不得静默丢弃记录。
- 写入将超过容量时明确拒绝该候选状态，保留旧状态和完整错误原因。历史资料可以另存为受控 artifact，但不得自动丢弃未解决项或自动创建新 Goal；容量调整需要独立的兼容性和资源测试。

### 4.2 规则权威与按需加载

Goal、Harness 的入口和核心适用范围统一为第 1 节的 Web 全栈开发与交付；新建/维护分类、七层编号、安全和用户确认边界不变。适用性、交付目标和风险裁剪直接引用第 5–9 节，不复制竞争规则。

Harness 单独维护执行材料的按需加载；Goal 只负责入口与交接，不平行枚举 Harness 执行参考清单。分类阶段不得读取完整交付台账、Guard 操作细节或执行层冷路径；checklists、exit/reentry 和专项审查分别在当前门禁、回退或风险触发时读取。相关安全约束必须在对应操作之前加载。

分类、交付契约、层门、验收和 Closure 必须各有单一规则权威。A 阶段登记责任组件、规范文件及校验入口；其他入口、输出模板和摘要只能引用或经校验生成，不形成第二份规范。规则责任沿用本节组件表，产品语义沿用本设计对应章节。

Agent context、LLM Tool/MCP 等领域路由移到 Harness 管理的明确按需参考，保留正向触发、排除条件和原有能力。不得静默删除功能、恢复禁用技能或更改个人交互偏好；行为变化必须列明，并遵守原审批边界。

## 5. Goal 交付契约

契约至少包含以下业务语义：

| 字段 | 含义与约束 |
| --- | --- |
| `revision` | 正整数；验收语义发生变化时递增 |
| `outcome` | 本轮可观察的用户或业务结果 |
| `actors` | 用户角色及相关权限边界，不填写凭据 |
| `flows` | 成功流程以及影响结果的失败、权限或恢复流程 |
| `non_goals` | 本轮明确不交付的内容 |
| `constraints` | 既有技术栈、兼容性、环境、数据和授权约束 |
| `unknowns` | 未解决问题、影响的决策和必须解决的时点 |
| `delivery_target` | `local-runnable`、`deployable` 或 `deployed` |
| `approval` | 已确认的契约 revision、确认来源及仍需确认的边界 |

验收项通过稳定 ID 引用该契约 revision。用户可以在设计阶段逐步细化未知项，不要求开局穷尽所有实现细节；但是影响当前操作安全或验收含义的关键未知项必须先解决。

### 5.1 契约修订

以下变化必须形成新 revision 并获得明确确认：删减必需验收项、降低行为要求、扩大权限、增加不可逆操作、扩大外部副作用，或改变约定交付目标。

纯粹澄清措辞且不改变验收语义的修改，记录修改原因即可；若无法判断是否改变语义，按需要确认处理。

记录中的“用户确认”是可追溯的授权记录，不是加密身份凭证。Agent 不得虚构用户确认，也不能把旧 revision 的确认套用到新 revision。

## 6. 业务切片与验收台账

### 6.1 业务切片

业务切片是一个可单独解释和验收的业务结果，不是按技术目录机械拆分的任务。

每个切片包含稳定 `slice_id`、目标结果、关联验收项、依赖切片，以及数据、API、UI、权限、部署五个面的适用性。各面标记为 `changed`、`reused` 或 `not_applicable`，并说明依据。

存量项目可以复用既有 UI、数据库或部署设施；没有修改某个面，不等于其契约无需检查。环境暂时不可用也不是“不适用”的理由。

依赖关系只用于确定验证前提与影响范围；拒绝悬空引用和循环依赖，不据此建设通用调度器。

### 6.2 验收项

每个验收项包含稳定 `criterion_id`、所属切片、契约 revision、可观察结果、是否必需、适用性依据、验证方式和证据引用。

验收项状态采用 `pending`、`in_progress`、`pass`、`fail`、`stale`、`blocked`、`not_applicable`。这些是交付明细状态，不替代 Goal 的 phase 或 Harness 的层门结果。

- `pass` 必须由当前证据和验收判断支持，不能只靠手写状态值。
- `stale` 表示原证据曾经成立，但当前适用条件已经失效。
- `blocked` 表示缺少执行条件或必要授权，不等同于验收失败。
- `not_applicable` 必须与已确认的契约范围一致，并保留依据；不得用来掩盖未完成的必需项。
- 可以有尚未执行的可选项，但必须披露，且不能遗留阻塞性风险。

进入交付验收时，至少存在一个适用的必需验收项。空台账、重复 ID、悬空证据、旧 revision 证据以及不支持的状态均不能形成接受结论。

## 7. 与现有七层框架的关系

不重排层号。用户目标和初步验收边界在 Goal Intake 明确；Layer 4 再形成一致的产品、API 和前端详细契约。

Layer 0–3 中的组件 MVP、独立探针和 Bridge 验证按本轮能力不确定性与集成风险决定适用范围。复用已验证能力时，必须给出当前仍适用的依据，不要求重新制作一套没有新增信息的演示脚本。

Layer 4 为本轮切片对齐数据、API、UI、权限及必要的运行约束；Layer 5 约束工程和发布纪律；Layer 6 完成实现、真实联调与验收。

安全、权限和秘密处理是横切约束，在首次相关操作前生效，不能等待某个较晚层完成后才生效。

未执行的检查如实记录为未执行或不适用。Gate 只有在适用检查均成立且排除依据有效时才能通过，不能把未执行记录改写成执行成功。

保留最小回滚：发现数据契约、拓扑或能力假设失效时，返回其所属最小上游层；不因局部失败重建所有层，也不凭没有证据的“影响不大”跳过回滚。

## 8. 证据合同与失效

### 8.1 三种不同材料

1. 执行声明：Agent 对行动与结果的文字描述。
2. 执行记录：实际观察到的命令或工具调用、运行结果和执行环境。
3. 验收结论：Harness 将执行记录与具体要求进行匹配后的判断。

三者分别记录来源，不允许通过重命名把声明升级成受观察的执行记录。退出码为 0 不能单独证明业务要求成立；仅有组件 mock 也不能替代要求真实依赖的联调证据。

执行记录至少关联验收项及契约 revision、验证入口、工作目录、起止时间、结果或退出状态、代码指纹、相关环境事实、观测来源以及输出引用或摘要。敏感数据不得进入普通日志；必要原始输出应受访问和保留约束。

证据原始文件可放在项目内受控的 `.codex/evidence/` 中，状态保存其内容摘要及引用。它们不被当作产品源码；由于该目录不属于普通工作区源码指纹范围，审计必须单独检查被引用证据的摘要，不能仅依赖源码指纹。

### 8.2 失效规则

以下事件使相关证据失效：源码或测试修改、生成源码或新增源码、契约 revision 变化、相关环境或外部依赖变化，以及上游回滚。

初版不做未经证明的精准影响分析。不能可靠确认某项证据仍适用时，保守地重验本轮受治理范围。历史证据保留为历史记录，但不得继续支撑当前 `pass`。

验证期间存在并发写入时，采用隔离的工作区或稳定快照；不能把首尾指纹相同当作“期间从未变化”的证明。无法证明验证针对稳定对象时，标记失效并重新执行。

外部依赖的版本、配置或数据条件无法确认时，不得宣称旧证据仍新鲜。事实重采集不要求抓取或保存凭据。

### 8.3 保证边界

Guard 的哈希、时间、序列与结构检查证明有限的一致性，不证明测试选得正确或输出没有被伪造。Windows 本轮继续为 `audit-only-windows`，不得升级描述成机械强制。

本轮不实现任意命令托管或签名证明。交付评测应利用独立定义的验收和实际执行观察补足自证风险，而不是扩大 Guard 的承诺。

## 9. Closure 与运行、部署事实

保持既有 `scope_result` 和 `operation_state` 字段；增加面向用户的验收摘要，列明通过、失败、失效、阻塞、不适用和未运行的项目。

本轮范围接受至少要求：所有适用的必需项通过且证据新鲜；相关跨层链路完成真实验证；关键权限和异常路径覆盖充分；没有未处理的高严重度风险；约定运行或部署方式可复现；剩余限制明确披露。

- `local-runnable`：已在约定本地环境验证核心流程，不等于已验证部署或生产就绪。
- `deployable`：交付配置与流程在约定隔离环境得到验证，不等于实际生产上线。
- `deployed`：在得到对应授权后完成目标环境部署，并有部署后检查证据。

“部署所需权限不可用”不能被写成“已经部署”。本轮范围验收与整个 bootstrap 退出分别判断；后者仍遵守既有稳定性、复现与退出条件，未满足时保持进行中。

## 10. 首轮验收矩阵

| ID | 场景 | 必须观察到的结果 |
| --- | --- | --- |
| WF-01 | 新建 Web 项目，没有指定框架 | 形成产品契约和选型约束，不从 Skill 中强制植入某个框架 |
| WF-02 | 在既有全栈仓库增加一个业务流程 | 保留现有技术栈，给出受影响切片与复用依据 |
| WF-03 | 页面成功但数据没有持久化 | 对应业务验收失败，不按页面或 HTTP 成功接受 |
| WF-04 | 未授权用户可以调用写接口 | 权限验收失败并阻止接受 |
| WF-05 | 只有关键词、总结文本或虚构探针列表 | 不能作为执行记录，也不能让交付验收通过 |
| WF-06 | 命令返回成功但没有覆盖对应要求 | 证据不足，不能形成对应项的 `pass` |
| WF-07 | 验证后代码、测试或契约发生变化 | 相关证据失效，不能复用旧接受结论 |
| WF-08 | 外部依赖条件变化或不可确认 | 相关项失效或阻塞，重新采集事实和验证 |
| WF-09 | 为迁就实现删除必需项或降低要求 | 未经新 revision 确认时拒绝接受 |
| WF-10 | 本轮确实不需要修改 UI 或部署 | 保留复用或不适用依据，不强造无关产物 |
| WF-11 | 仅完成可部署交付，却声称已生产上线 | 拒绝混淆目标与事实；真实上线需授权和回归证据 |
| WF-12 | 旧状态、旧项目与禁用的 GSD | 不自动迁移、不恢复 `.agents`，必要时走原 Harness 路径 |
| WF-13 | Guard 没有声明新交付扩展能力 | 新模式不可启用，不能静默退回较弱验收后声称成功 |
| WF-14 | 删除活动运行的交付扩展以绕过检查 | 状态转换被拒绝；Windows 只报告真实可用的审计保证 |
| WF-15 | 只有 mock 验证，实际 API 或数据库失败 | 真正要求联调的验收不能通过 |
| WF-16 | 验证期间并发修改或证据文件内容被替换 | 不能接受无法绑定稳定代码与原始结果的证据 |
| WF-17 | 空验收集、重复 ID、悬空引用或超过容量 | 明确拒绝无效候选，保留原状态，不通过空集或静默截断接受 |

评测分为三个独立等级：结构与契约校验、受观察事件回放、真实 Web 全栈夹具运行。报告必须标明实际运行等级；未执行的等级为 `not-run`，不得从低等级通过推导高等级通过。

真实夹具至少包含页面、服务接口、数据持久化及权限边界，并在隔离测试环境运行。夹具采用哪种技术栈属于测试工程选择，不构成对用户项目的默认技术栈要求。测试定义不得由被评测 Agent 随意删除或放宽。

首轮记录任务完成率、假完成情况、人工介入、重验成本、耗时及可获取的 token 数据；缺少数据时明确缺失，不填零、不承诺尚未测出的收益。

### 10.1 结构与上下文补充验收

WF-01–WF-17 及三个独立评测等级全部保留。新增结构验收覆盖：新建 Web 项目；存量项目仅改 API 并复用 UI/部署；分类不提前读执行冷路径；实际门禁、回退和安全操作前能加载必要参考；专项路由不退化；字段与安全不变量严格而等价自然语言解释不被无故拒绝。

## 12. 当前基线事实与设计风险

源码摘要见同目录 `2026-09-08-web-fullstack-source-baseline.json`。执行实现前应重新核对摘要，发现并发修改时先审阅差异，不覆盖他人工作。

已确认的限制包括：当前协议仍使用 state schema 1；旧行为评分主要检查文本；当前 Guard 不能证明命令诚实执行；现有台账要求在不同文件中的强制程度尚不一致。

本次文档工作还观察到：Goal Protocol JSON 允许 `classified -> executing`，但已安装 Guard 拒绝非相邻转换。当前工作使用更严格的 `classified -> planned -> executing`。实施计划必须把该差异列入兼容性对齐检查，不能仅凭 capability major 匹配宣称行为完全兼容。

2026-09-08 的用户交接报告指出，任务「完成 Goal Harness 下一阶段开发」（`01a07b9b-9b28-7740-88ed-17669c42b6b9`）在其独立 Goal Protocol v2 source repo 开展 Foundation/Adapter 工作。本次文档纳入未重新审计其运行状态，也不停止该任务或覆盖其源码。详细计划须登记基线/接口协调风险；本设计仍由当前任务唯一集成，接入或安装前重新核对双方源码摘要、目标来源和协议差异，不把另一仓库的最新文件默认为本轮基线。

主要残余风险及处理原则：

- 规则增加导致用户负担：只加载当前业务切片需要的材料，区分用户摘要和机器记录。
- 验收自证：保持独立要求与受观察执行，明确未验证的部分，不将签名或哈希当成业务正确性。
- 新旧状态静默混用：能力检查、初始化绑定、禁止活动运行降级、保留旧状态回归。
- 状态过大或证据循环失效：保存有界摘要与引用，单独校验证据内容，不把验证报告当作产品源码反复污染指纹。
- 通用性宣传超过验证：公开实际运行过的技术组合与案例，不把契约层可表达性描述成普遍交付能力。
